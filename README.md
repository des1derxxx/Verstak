# Verstak

Рабочее пространство для проектов, задач и заметок. Первая версия веб-приложения с аккаунтами и совместной работой.

## Стек

- Next.js 16 (App Router), TypeScript, Tailwind CSS 4.
- Axios: общий клиент с cookie, CSRF, таймаутом и обработкой ошибок.
- Python 3.12, FastAPI, официальный драйвер PyMongo.
- MongoDB с replica set для транзакций.
- Nginx и Docker Compose для запуска.

У каждого приложения свои зависимости, настройки сборки, Dockerfile и тесты. Для изменения задачи начни с `backend/app/api/routes/tasks.py`: маршрут вызывает сервис из `services/tasks/operations.py`, общая запись и проверка связей находится в `services/tasks/mutations.py`, доступ — в `services/tasks/access.py`. Тот же механизм записи используется синхронизацией рабочего пространства. `main.py` собирает зависимости и маршруты.

На фронтенде экран аккаунта находится в `features/account/`, задачи — в `features/tasks/`. Повторно используемые дропдауны, модальные окна, Markdown и аватарки — в `shared/ui/`. API-клиент находится в `shared/api/client.ts`. В `app/` находятся серверные страницы и layout Next.js; `application/WorkspaceRouter.tsx` связывает URL и клиентское состояние пространства. Начальные данные и доступ проверяет серверный Axios-клиент `shared/api/server.ts`. Состояние и запросы вынесены в хуки, секции экранов — в отдельные компоненты.

## Маршруты и возможности Next.js

Страницы объявлены папками и `page.tsx` в App Router. Скобки `(auth)` и `(workspace)` группируют код и не входят в URL.

| URL | Страница |
| --- | --- |
| `/login`, `/register` | Вход и регистрация |
| `/forgot-password`, `/reset-password` | Восстановление доступа |
| `/invite` | Принятие приглашения |
| `/workspaces/new` | Создание пространства |
| `/workspaces/[workspaceId]/board`, `/backlog`, `/list`, `/pages`, `/today` | Представления пространства (последние сегменты относительно того же пространства) |
| `/workspaces/[workspaceId]/projects/[projectId]/board` | Проект; также доступны `backlog`, `list`, `pages` |
| `/workspaces/[workspaceId]/tasks/[id_or_key]` | Карточка задачи, например `OM-52` |
| `/workspaces/[workspaceId]/pages/[noteId]` | Страница документации |
| `/workspaces/[workspaceId]/settings/profile`, `/settings/members`, `/settings/tokens`, `/settings/data` | Настройки относительно пространства |
| `/workspaces/[workspaceId]/notifications` | Уведомления |

Layout пространства проверяет сессию и членство на сервере, параллельно загружает снимок и участников и передаёт начальные данные клиентским компонентам. Шапка, меню и состояние пространства сохраняются между страницами. Сервер обращается к Python API через отдельный Axios-клиент с cookie текущего запроса. `API_INTERNAL_ORIGIN` по умолчанию равен `http://127.0.0.1:8000`; Compose задаёт `http://api:8000`. Секреты и адрес внутреннего API не передаются в браузер.

Используются серверные компоненты, `Link`, предварительная загрузка основных разделов, отдельные компоненты представлений, загрузка редакторов через `next/dynamic`, `loading.tsx`, `error.tsx`, `not-found.tsx` и метаданные страниц. Карточка задачи использует parallel/intercepting routes: переход с доски открывает drawer поверх текущего экрана, прямое открытие или обновление ссылки — отдельную страницу. Массовая предварительная загрузка всех карточек отключена.

`React.cache` устраняет повторные серверные запросы в пределах одного рендера. Приватные страницы динамические, со свежим CSP nonce, и не помещаются в общий межпользовательский кэш. Сессия остаётся в HttpOnly/SameSite cookie, теперь с `Path=/`, чтобы серверные страницы могли проверить её. CSRF и проверка прав остаются в Python API. После обновления старой версии может потребоваться снова войти; вход и выход очищают прежнюю cookie с `Path=/api`.

Черновики защищены при переходах, закрытии и обновлении страницы; фоновое обновление снимка при несохранённых правках приостановлено. Сервер передаёт исходную дату для согласованного SSR, после загрузки используется часовой пояс браузера. Старые ссылки `/#invite=…` и `/#reset=…` перенаправляются на соответствующие страницы; секреты остаются во фрагменте URL.

- Markdown в задачах, комментариях и страницах: списки, таблицы, код и безопасный предпросмотр.

## Быстрый запуск

Нужны Docker Desktop с Compose и Python 3 для генерации локального `.env`.

```sh
cd /Users/ivanralo/dev/GitHub/Verstak
python3 scripts/setup_env.py
docker compose up --build -d
```

Открой **http://localhost:8080**, зарегистрируйся и создай первый проект. На первом запуске Docker скачает образы и зависимости. MongoDB и API наружу не публикуются.

После перехода на Next.js пересобери стек целиком:

```sh
docker compose up -d --build
```

API автоматически мигрирует существующие задачи: UUID и связи сохраняются, задачи получают ключи и собственную `revision`. Старые завершённые задачи сохраняют статус без выдуманных комментариев и авторов. Миграция идемпотентная, один раз поднимает версию пространства; заранее сделай полную резервную копию MongoDB. Префикс для старых проектов выбирается по названию (`Verstak` → `VERSTAK`), для новых его можно задать в форме проекта.

Для последующих изменений только интерфейса пересобирается сервис `frontend`:

```sh
docker compose up -d --build frontend
```

Затем обнови страницу в браузере. `C` открывает создание задачи, `/` или `Cmd/Ctrl+K` — поиск. В редакторе `Cmd/Ctrl+Enter` сохраняет задачу; `Esc` закрывает окно с проверкой несохранённых изменений. Проект и представление определяются URL: прямые ссылки, обновление страницы и история браузера сохраняют нужный экран. Поиск, приоритет, статус и сортировка хранятся в query-параметрах; их изменение использует встроенную интеграцию Next.js с History API без повторной загрузки снимка.

`setup_env.py` создаёт уникальные пароли MongoDB, ставит права `600` на `.env` и сохраняет существующий файл без изменений. `.env` исключён из Git. Не меняй пароли в нём после создания MongoDB без соответствующей смены паролей пользователей базы.

Проверка состояния и логи:

```sh
docker compose ps
docker compose logs --tail=100 api
docker compose logs --tail=100 mongo-init
```

Остановка с сохранением данных:

```sh
docker compose down
```

Данные базы хранятся в именованных Docker volumes. Флаг `down -v` удаляет их.

## Профиль

Нажми на аватарку справа в шапке или на своё имя внизу бокового меню. Можно изменить имя, email и текст «О себе», загрузить фото или удалить его. Несохранённые правки защищены от случайного закрытия. Профиль доступен и наблюдателям: роль пространства не ограничивает личные настройки.

При смене email нужен текущий пароль. Новый адрес должен быть свободен; после сохранения вход выполняется по нему. Другие сессии и ранее выданные ссылки восстановления отзываются, текущая сессия остаётся активной. Как и при регистрации, подтверждение почтового ящика пока не реализовано.

Форма принимает PNG, JPEG и WebP до 10 МБ и 40 мегапикселей, обрезает фото по центру и уменьшает перед отправкой. API повторно декодирует изображение, убирает метаданные и сохраняет статичный WebP 256×256 в отдельной коллекции `avatars` в MongoDB. Внешнее файловое хранилище не требуется. Фото видно самому пользователю и участникам общих пространств; без входа оно недоступно. Аватарки входят в полную резервную копию MongoDB, а в JSON-экспорт проектов не входят.

`PATCH /api/auth/profile` принимает `revision`, `name`, `email`, `bio`, при смене email — `currentPassword`. Опциональное `avatarData` — data URL PNG/JPEG/WebP до 2 МБ и 16 мегапикселей; `null` удаляет фото, отсутствие поля сохраняет текущее. Для профиля нужна cookie-сессия с CSRF; API-токены этот маршрут не открывают. `profileRevision` защищает от затирания правок из другого окна; конфликт возвращает `409`.

## Приглашение участника

1. Владелец открывает «Участники пространства» в боковом меню.
2. Указывает email и роль, создаёт и копирует ссылку.
3. Участник открывает ссылку, входит или регистрируется с указанным email и принимает приглашение.

Приложение создаёт ссылку; письмо автоматически не отправляется. Приглашение привязано к email и принимается один раз. Редактор может менять проекты и задачи; наблюдатель может читать и экспортировать данные. Управлять участниками, приглашениями и полным импортом может владелец.

## Разработка

Фронтенд, из корня репозитория:

```sh
cd frontend
corepack enable
pnpm install --frozen-lockfile
pnpm dev
```

Next.js работает на `http://localhost:3000` и в режиме разработки проксирует `/api` на `http://127.0.0.1:8000`. В Docker Nginx принимает запросы на `http://localhost:8080`: страницы направляются в `frontend:3000`, API — в `api:8000`. Cookies остаются в одном origin; Nginx перезаписывает `X-Forwarded-For` для API.

Для локального запуска Python API нужна доступная MongoDB с replica set или MongoDB Atlas. Все соединения с MongoDB остаются на сервере.

Из корня репозитория, в отдельном терминале:

```sh
cd backend
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

Установи переменные окружения `MONGODB_URI`, `MONGODB_DATABASE=verstak` и `PUBLIC_ORIGIN=http://localhost:3000`, затем запусти:

```sh
.venv/bin/python -m uvicorn app.main:app --reload
```

URI держи в окружении или локальном файле секретов. API читает переменные окружения процесса; файл `.env` в корне автоматически использует Docker Compose. У standalone MongoDB транзакции недоступны, поэтому API явно откажется запускаться с такой конфигурацией.

Документация OpenAPI и схемы запросов при локальном запуске: `http://127.0.0.1:8000/docs`. Браузерные запросы, меняющие данные, используют `X-Verstak-Client: web`, JSON и после входа `X-CSRF-Token` из `/api/auth/me`. Браузерный клиент устанавливает их сам.

## Соглашения фронтенда

- Компоненты, хуки и утилиты — типизированные стрелочные функции.
- Стили — Tailwind в компонентах. В `app/globals.css` находятся только токены, базовые стили элементов и настройки доступности.
- Общие кнопки и иконки-кнопки — `shared/ui/Button.tsx`; цвета статусов — `shared/ui/variants.ts`.
- `shared/api/client.ts` создаёт Axios instance с CSRF, cookie и таймаутом 15 секунд. Компоненты используют этот клиент; типы DTO находятся в `shared/api/types.ts`, синхронизация пространства — в `shared/api/workspaces.ts`.
- `features/workspaces/WorkspaceView.tsx` собирает секции экрана. Загрузка, права, изменения и конфликты находятся в `hooks/useWorkspaceController.ts`.
- Редактор задачи разделён на секции в `features/tasks/task-editor/`, состояние — в `useTaskEditor.ts`.
- `application/useApplication.ts` управляет сессией и пространствами. Чтение URL и localStorage выполняется с учётом серверного рендера; начальное состояние приложения можно отрендерить без browser API.
- Форматирование: `pnpm format`; проверка: `pnpm format:check`. Зависимости фронтенда устанавливаются внутри `frontend/`.

Production-сборка: `pnpm build`, standalone-артефакт — `.next/standalone`, запуск проверенного контейнера использует `node server.js`. Для локальной проверки production-сборки — `pnpm start`. Next.js генерирует отдельный nonce для script-src в CSP и динамически рендерит страницу; внешние шрифты и CDN не требуются. Схема развёртывания следует [standalone output Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/output), подключение Tailwind — [официальному руководству](https://tailwindcss.com/docs/installation/framework-guides/nextjs).

## Задачи и интеграции

При создании проекта укажи ключ из 2–10 латинских заглавных букв/цифр, начиная с буквы, например `OM`. Сервер атомарно выдаёт `OM-1`, `OM-2`… Номера не переиспользуются после удаления, ключ задачи сохраняется при правках. После выдачи номеров ключ проекта фиксируется; перенос задачи между проектами пока не поддерживается. Внешний ключ подходит для веток (`OM-52-fix-login`), PR и коммитов, внутренний UUID продолжает связывать записи.

Подзадача — самостоятельная задача с `parentId` (UUID), своим статусом, номером и обсуждением. Родитель находится в том же проекте, циклы запрещены, глубина до 32 задач. Родителя нельзя закрыть с незавершёнными подзадачами или удалить, пока к нему привязаны дети. В карточке есть создание подзадачи и переход к связанным задачам.

Любой переход в `done`, включая создание завершённой задачи, требует `resolutionComment`. Сервер одновременно сохраняет статус, итоговый комментарий и историю. После повторного открытия нужен новый итог. Обычный комментарий отправляется отдельно, черновик защищён от случайного закрытия. Наблюдатель читает обсуждение и историю, писать может редактор или владелец. Комментарии и события истории сейчас неизменяемые; редактирования и удаления комментариев нет.

В боковом меню открой **API-токены**, выбери название, права и срок. Скопируй секрет сразу: повторно сервер его не возвращает. Хранится только SHA-256-хеш. Токен привязан к одному пространству; текущие права создателя проверяются при каждом запросе. Понижение роли, удаление участника, истечение срока или отзыв прекращают соответствующий доступ.

Пример для бота (значения переменных задай локально, токен не коммить):

```sh
export VERSTAK_URL=http://localhost:8080
# VERSTAK_TOKEN — секрет из интерфейса
curl "$VERSTAK_URL/api/projects" -H "Authorization: Bearer $VERSTAK_TOKEN"

# projectId — UUID проекта из предыдущего ответа
curl -X POST "$VERSTAK_URL/api/tasks" \
  -H "Authorization: Bearer $VERSTAK_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"projectId":"PROJECT_UUID","title":"Исправить вход","type":"bug","description":"## Проверить\n- [ ] Вход по email"}'

# revision берётся из GET задачи; при 409 прочитай её заново и согласуй правку
curl -X PATCH "$VERSTAK_URL/api/tasks/OM-52" \
  -H "Authorization: Bearer $VERSTAK_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"revision":1,"status":"done","resolutionComment":"Исправлено в PR #52, вход проверен"}'
```

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/projects` | Проекты с UUID и ключами |
| `GET /api/tasks` | `{items,total,limit,offset}`, фильтры `projectId`, `parentId`, `status`, лимит до 200 |
| `POST /api/tasks` | Создать; ответ — задача с серверными `id`, `key`, `revision` |
| `GET /api/tasks/{id_or_key}` | Прочитать по UUID или `OM-52` |
| `PATCH /api/tasks/{id_or_key}` | Частичная правка, обязательная `revision`; `null` очищает parentId/assigneeId |
| `DELETE /api/tasks/{id_or_key}?revision=…` | Удалить с проверкой версии |
| `GET/POST /api/tasks/{id_or_key}/comments` | Обсуждение; POST `{body: "Markdown"}` |
| `GET /api/tasks/{id_or_key}/history` | Автор, время, событие и изменённые поля |

Bearer-запросам не нужны cookie, CSRF или `X-Verstak-Client`. Остальные маршруты управления аккаунтом, пространством и токенами требуют браузерную сессию с CSRF. Для cookie-доступа к REST указывай `workspaceId` в query, а при `POST /tasks` — в JSON; bearer определяет пространство сам. Документация API доступна через `/api/docs`, схема OpenAPI — через `/api/openapi.json`. Повторный POST создаёт новую задачу: автоматическую повторную отправку после неопределённого сетевого результата пока нужно обрабатывать на стороне интеграции.

История фиксирует создание, правки, статус, комментарии и удаление задачи, независимо от того, пришло изменение из UI или REST. При назначении, правках и комментариях уведомления получают автор задачи, текущий исполнитель и участники обсуждения, кроме самого автора действия. Раздел **Уведомления** показывает последние 100 событий с текущим доступом к пространствам. Email/push-рассылки и уведомления в реальном времени пока отсутствуют.

## Восстановление пароля

В существующий `.env` добавь настройки провайдера почты (секреты только локально):

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=verstak@example.com
SMTP_PASSWORD=APP_PASSWORD_FROM_PROVIDER
SMTP_FROM=Verstak <verstak@example.com>
SMTP_SECURITY=starttls
```

Для TLS с момента подключения используй `SMTP_SECURITY=ssl` и порт провайдера, обычно `465`. Сертификаты проверяются, открытого SMTP без TLS нет. Затем выполни `docker compose up -d --build api`; API подключён к сети с выходом к SMTP. `PUBLIC_ORIGIN` должен совпадать с адресом приложения: из него строится ссылка восстановления.

«Забыл пароль?» на странице входа отправляет одноразовую ссылку на 30 минут. Ответ не раскрывает существование аккаунта. Секрет в URL-фрагменте, в базе только хеш, есть ограничения частоты. После успешного сброса отзываются все сессии, API-токены и ссылки восстановления этого аккаунта, затем требуется вход с новым паролем. Без настроенного SMTP интерфейс сообщает о недоступной отправке; сброс не выдаёт токены через API. Реальную доставку нужно проверить с выбранным провайдером. Приглашения по-прежнему отправляются владельцем вручную.

## Проверки

Из корня репозитория:

```sh
pnpm --dir frontend format:check
pnpm --dir frontend typecheck
pnpm --dir frontend test
pnpm --dir frontend build
backend/.venv/bin/python -m pytest backend/tests -q
docker compose config --quiet
# После запуска Docker-стека:
python3 scripts/smoke_stack.py
```

Для изолированного тестового Compose-стека доступен `python3 scripts/smoke_stack.py --exercise`: он создаёт тестовый аккаунт, проект и задачу и проверяет прямые приватные страницы и выход. На рабочей базе запускай обычную проверку без этого флага.

По умолчанию проверки API используют транзакционное тестовое хранилище. Оно проверяет бизнес-логику и права доступа, но не заменяет интеграционную проверку MongoDB. Чтобы выполнить те же тесты на реальной базе, задай `VERSTAK_TEST_MONGODB_URI` с URI тестового replica set. Каждый тест создаёт и удаляет отдельную базу с префиксом `verstak_test_`; используй отдельную тестовую MongoDB с правами на создание этих баз.

Фронтенд проверяется также компонентными тестами в jsdom: профиль, загрузка фото, клавиатурное управление и поиск в дропдауне, быстрый ввод, повтор сохранения после ошибки, права наблюдателя, горячие клавиши, работа с бэклогом и черновиками. Эти тесты проверяют взаимодействия и не заменяют визуальную проверку в браузере.

GitHub Actions собирает фронтенд, запускает тесты, поднимает MongoDB replica set и повторяет проверки API на реальной базе. Отдельная проверка запускает полный Compose-стек, проверяет HTML, CSP и Tailwind-ресурсы, создаёт тестовый аккаунт и проверяет авторизованный SSR и прямые маршруты, затем пересоздаёт API и фронтенд и проверяет, что Nginx продолжает обслуживать приложение.

## Модель данных

| Коллекция | Содержимое |
| --- | --- |
| `users` | Имя, нормализованный email, описание, версия профиля/аватара, Argon2id-хеш пароля |
| `avatars` | Нормализованные WebP-изображения, отдельно от документов аккаунтов |
| `workspaces` | Название и номер версии данных |
| `members` | Связь пользователя с пространством и роль |
| `projects` | Проекты с `workspace_id` |
| `tasks` | UUID, постоянный key, revision, parentId, assigneeId, type, links, Markdown и чеклист |
| `project_keys`, `issue_keys` | Счётчики и постоянные резервации номеров, включая удалённые задачи |
| `comments`, `history` | Обсуждение и аудит с автором и серверным временем |
| `notifications` | Уведомления участников и отметки прочтения |
| `api_tokens`, `password_resets` | Хеши токенов, права/пользователь, срок действия |
| `notes` | Заметки с `workspace_id` и `projectId` |
| `sessions` | Хеш токена сессии, CSRF-токен, срок действия |
| `invitations` | Хеш одноразового токена, email, роль, пространство и срок |
| `rate_limits` | Счётчики ограничений регистрации, входа и приглашений |

API проверяет членство в пространстве на каждом запросе. Изменения нескольких документов выполняются в MongoDB-транзакциях. Удаление проекта удаляет его задачи и заметки в той же транзакции. Секреты сессий и приглашений хранятся как SHA-256-хеши; пароли — в формате Argon2id PHC с индивидуальной случайной солью.

`PATCH /api/workspaces/{id}/data` передаёт изменённые документы и удалённые ID. Номер версии защищает от потерянных изменений: устаревшая запись получает `409`, текущая версия загружается, открытый черновик сохраняется для повторного действия. Полная замена при импорте использует `PUT` и те же транзакции. Уникальные и TTL-индексы создаются идемпотентно при запуске API; сроки сессий, приглашений, API-токенов и ссылок сброса также проверяются в запросах, независимо от времени очистки TTL.

Первая версия загружает снимок пространства для локального поиска и фильтров. Обновление выполняется при возвращении в окно, каждые 30 секунд без открытого редактора и вручную. Для больших пространств понадобятся серверная пагинация и поиск. Живое одновременное редактирование текста пока не реализовано.

## Подготовка серверного размещения

В `.env` укажи реальный адрес, например:

```dotenv
PUBLIC_ORIGIN=https://verstak.example.com
APP_ENV=production
COOKIE_SECURE=true
ALLOW_REGISTRATION=false
```

Перед Nginx приложения поставь HTTPS reverse proxy, направляющий запросы на локальный порт 8080. При `APP_ENV=production` API требует HTTPS origin и Secure cookies. `ALLOW_REGISTRATION=false` сохраняет регистрацию по действующим приглашениям; сначала создай аккаунт владельца. MongoDB и API должны оставаться во внутренней сети. Доверие API к proxy-заголовкам рассчитано на Nginx из Compose, который перезаписывает `X-Forwarded-For`.

Экспорт JSON сохраняет только проекты, задачи и заметки одного пространства, включая новые поля и связи задач. Комментарии, историю, резервации удалённых номеров, уведомления и токены он не содержит. Для полного восстановления с аккаунтами, ролями и сессиями настрой резервное копирование MongoDB через `mongodump`/`mongorestore` или средство резервирования выбранного MongoDB-хостинга.

До публичного использования стоит добавить подтверждение email: в этой версии email служит идентификатором аккаунта, подтверждение владения почтовым ящиком ещё не реализовано. Перед первым размещением выполни интеграционные тесты на выбранной MongoDB и проверь HTTPS-конфигурацию.
